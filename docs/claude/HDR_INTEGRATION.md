# HDR fusion — วิธีเชื่อมโมดูลเข้ากับขั้น merge

เอกสารนี้อธิบายโมดูล `th.ogay.luma.hdr.HdrFusionQuality` (งาน Claude B ใน `docs/CLAUDE_HANDOFF.md`) ว่าทำอะไร ไม่ทำอะไร และ Codex ต้องเรียกใช้อย่างไรเพื่อแทนขั้นรวมภาพ HDR โมดูลนี้ไม่แก้ `HdrCapture.kt`, `FrameFusionEngine.java`, Gradle หรือ UI

ณ commit ที่ส่งงาน (`9ba0844` ของ `v0.3-studio`) ไฟล์ `HdrCapture.kt` ยังไม่อยู่ใน branch ขั้นตอนด้านล่างจึงเขียนตามสัญญา API ในเอกสารส่งต่อ ไม่ได้อิงโค้ด HDR capture จริง

## โมดูลทำอะไร

โมดูลรับภาพ bracket หลายระดับแสงที่เป็น JPEG ถอดรหัสแล้ว (ARGB8888) และคืนภาพ SDR หนึ่งภาพที่ดึงรายละเอียดจากภาพที่แสงพอดีที่สุดในแต่ละบริเวณ ตัวอย่างเช่น หน้าต่างที่ขาวโพลนในภาพ EV 0 จะได้ลายจากภาพ EV −2 ส่วนมุมห้องที่ดำในภาพ EV 0 จะได้รายละเอียดจากภาพ EV +2

วิธีรวมภาพคือ exposure fusion ของ Mertens, Kautz และ Van Reeth (2007) ซึ่งให้น้ำหนักแต่ละพิกเซลจากความคมชัด (contrast) ความอิ่มสี (saturation) และความใกล้ระดับแสงกลาง (well-exposedness) แล้วผสมผ่าน Laplacian pyramid เพื่อไม่ให้เกิดรอยต่อหรือขอบเรืองแสง (halo) ที่รอยเปลี่ยนน้ำหนัก

สิ่งที่โมดูลเพิ่มจากวิธีของ Mertens มีสามเรื่อง

1. ปฏิเสธการเคลื่อนไหว (motion rejection) โดยอิงภาพอ้างอิง frame 0 ก่อนเทียบ โมดูลแปลงความสว่างของภาพอ้างอิงไปเป็นระดับแสงของภาพอื่นด้วย intensity mapping function ซึ่งสร้างจาก cumulative histogram ของบริเวณที่ภาพซ้อนกัน บริเวณที่ค่าไม่ตรงกับที่คาดจะได้น้ำหนักเป็นศูนย์ แล้วขยายบริเวณนั้นอีก 2 พิกเซลทุกทิศ (erosion 5×5) เพื่อไม่ให้ขอบวัตถุที่ขยับทิ้งเงาซ้อน (ghost)
2. รับมือบริเวณที่ภาพอ้างอิง clip ตรงที่ภาพอ้างอิงขาวจนสุด (luma ≥ 250) ระบบเทียบค่าแบบด้านเดียว คือภาพที่มืดกว่าต้องสว่างอย่างน้อยเท่าค่าที่ระดับ 250 แปลงไปได้ ตรงที่ภาพอ้างอิงดำจนสุด (luma ≤ 5) ภาพที่สว่างกว่าต้องไม่สว่างเกินค่าที่ระดับ 5 แปลงไปได้
3. จำกัดหน่วยความจำ โมดูลประมวลผลเป็นแถบแนวนอน (strip) ที่มีขอบซ้อน (halo) กว้าง 2^(levels+1) แถว แถบแต่ละแถบเริ่มที่แถวซึ่งตรงกับกริดของ pyramid ชั้นหยาบสุด ผลจึงเท่ากับการประมวลผลทั้งภาพทุกพิกเซล (เทสต์ `stripsMatchWholeFrameProcessing` ตรวจว่าต่างกัน 0)

## สิ่งที่โมดูลไม่ทำ

โมดูลไม่สร้างภาพ HDR แบบ radiance, Ultra HDR หรือ gain map เพราะ JPEG ผ่าน tone curve ที่ไม่รู้ค่า รวมถึง local tone mapping และ sharpening ของ ISP แล้ว ผลลัพธ์จึงเป็นภาพ SDR 8 บิตเท่านั้น ห้ามติดป้าย Ultra HDR หรือ HDR10 ให้ไฟล์นี้

โมดูลไม่จัดตำแหน่งภาพเอง ผู้เรียกต้องส่ง `dx/dy` มา และรองรับเฉพาะการเลื่อนเป็นจำนวนเต็มพิกเซล ไม่รองรับการหมุน การบิดจาก rolling shutter หรือการเลื่อนครึ่งพิกเซล การเลื่อนไม่เกินหนึ่งพิกเซลที่ขอบวัตถุ โมดูลรับได้เพราะการเทียบใช้ค่าที่ใกล้ที่สุดในหน้าต่าง 3×3

การตรวจการเคลื่อนไหวใช้ luma อย่างเดียว วัตถุที่เปลี่ยนสีแต่ความสว่างเท่าเดิมจึงหลุดการตรวจได้

## สัญญา API

```java
public static int[] merge(int[][] frames, int width, int height,
                          int[] dx, int[] dy, float[] exposureEv)
```

`frames[i]` เป็น ARGB8888 แบบ row-major ขนาด `width * height` ทุกภาพ โมดูลไม่สนใจค่า alpha ของอินพุต และคืนภาพที่ alpha เป็น 0xff ทุกพิกเซล `frames[0]` เป็นภาพอ้างอิง ต้องมี `dx[0] == 0` และ `dy[0] == 0` ส่วน `dx[i], dy[i]` หมายความว่าจุด `(x, y)` ของภาพอ้างอิงอยู่ที่ `(x + dx[i], y + dy[i])` ในภาพ i ซึ่งเป็นทิศเดียวกับที่ `FrameFusionEngine.align(reference, candidate, ...)` คืนมา

`exposureEv[i]` ต้องเป็นค่าจำกัด (ไม่ใช่ NaN หรือ infinity) โมดูลใช้แค่เครื่องหมายของ `exposureEv[i] - exposureEv[0]` เพื่อรู้ว่าภาพไหนสว่างกว่าในการเทียบด้านเดียวตรงบริเวณ clip ส่วนความสัมพันธ์ของความสว่างจริง โมดูลวัดจากพิกเซล

โมดูลโยน `IllegalArgumentException` เมื่อจำนวนภาพเป็น 0 หรือเกิน 9 ภาพ (`MAX_FRAMES`) เมื่อขนาดภาพไม่เป็นบวกหรือเกิน 50 ล้านพิกเซล (`MAX_PIXELS`) เมื่อความยาว array ไม่ตรงกัน เมื่อ frame 0 ถูกเลื่อน และเมื่อ EV ไม่ใช่ค่าจำกัด ภาพที่ไม่ซ้อนกับภาพอ้างอิงเลยจะถูกข้ามโดยไม่โยน exception

มี API เพิ่มจากสัญญาเดิมสองตัว ทั้งสองตัวเป็นส่วนขยาย ไม่ได้เปลี่ยนสัญญาเดิม

- `merge(..., long workingBytes)` กำหนดเพดานหน่วยความจำทำงานเอง ค่าเริ่มต้นคือ `DEFAULT_WORKING_BYTES` = 96 MiB
- `matchHistogram(int[] referenceLuma, int[] candidateLuma)` แปลง luma ของภาพอื่นให้อยู่ในระดับความสว่างของภาพอ้างอิง ใช้ก่อนหา `dx/dy` (ดูหัวข้อถัดไป)

## วิธีแทนขั้น merge

ลำดับนี้ทำบน worker thread เท่านั้น เพราะ `merge` ทำงานแบบ blocking

1. ถอดรหัสทุกภาพเป็น `Bitmap` ขนาดเท่ากัน แล้วอ่านพิกเซลด้วย `getPixels` ลงใน `int[]`
2. ย่อภาพเป็นภาพเล็กประมาณ 256×192 แล้วแปลงเป็น luma เหมือนที่ `MultiFrameFusion.thumbnail` ทำอยู่
3. **เรียก `HdrFusionQuality.matchHistogram(refLuma, candLuma)` ก่อน** แล้วจึงเรียก `FrameFusionEngine.align(refLuma, matched, w, h)` เหตุผลคือ `align` วัดผลต่างสัมบูรณ์ของ luma ซึ่งใช้ไม่ได้เมื่อสองภาพต่างระดับแสง ในเทสต์ `histogramMatchingLetsTranslationSearchHandleExposureDifferences` ภาพ EV −2 ที่เลื่อน (4, −3) ได้ alignment error 50.6 เมื่อไม่ match ซึ่งเกินเกณฑ์ 22 ที่ `MultiFrameFusion` ใช้ทิ้งภาพ แต่หลัง match ได้ error 1.0 และตำแหน่งถูกต้อง
4. คูณ `dx/dy` จากภาพเล็กด้วยอัตราส่วนขนาดภาพจริงต่อภาพเล็ก แล้วปัดเป็นจำนวนเต็ม แบบเดียวกับ `MultiFrameFusion.process`
5. คำนวณ `exposureEv` จาก `CaptureResult` ของแต่ละภาพ เช่น `log2(SENSOR_EXPOSURE_TIME × SENSOR_SENSITIVITY)` ลบด้วยค่าของ frame 0 แนะนำให้ใช้ค่าที่กล้องรายงานแทนค่าที่ขอ เพราะ AE อาจไม่ได้ใช้ค่าที่ขอจริง
6. เรียก `HdrFusionQuality.merge(frames, w, h, dx, dy, ev)` แล้วสร้าง `Bitmap` จากผลลัพธ์ด้วย `Bitmap.createBitmap(out, w, h, ARGB_8888)`
7. ติด metadata ให้ตรงกับความจริง เช่น EXIF Software เป็น "Luma HDR fusion (SDR)" ไม่ใช่ Ultra HDR

ตอนนี้ `merge` ยกเลิกกลางทางไม่ได้ เพราะสัญญาในเอกสารส่งต่อไม่ได้กำหนด callback ยกเลิกไว้ อย่าแก้ปัญหานี้ด้วยการตัดภาพเป็นชิ้นแล้วเรียก `merge` ทีละชิ้น เพราะแต่ละชิ้นจะได้ histogram และ pyramid ของตัวเอง ผลจึงเกิดรอยต่อ ถ้าต้องการยกเลิกได้ ผมเสนอให้เพิ่ม overload ที่รับ `java.util.function.BooleanSupplier stopped` และตรวจค่าระหว่างแถบ ซึ่งต้องตกลงกันใน PR ก่อนแก้

## หน่วยความจำและเวลา

หน่วยความจำรวมเท่ากับอินพุต + เอาต์พุต + เพดานทำงาน อินพุตใช้ N × กว้าง × สูง × 4 ไบต์ เอาต์พุตใช้ กว้าง × สูง × 4 ไบต์ ตัวอย่างเช่น ภาพ 12 MP จำนวน 3 ภาพ ใช้อินพุต 144 MB เอาต์พุต 48 MB และเพดานทำงาน 96 MiB รวมราว 290 MB

ที่ 4000×3000 กับเพดานเริ่มต้น โมดูลใช้ pyramid 5 ชั้น แถบละ 256 แถว และขอบซ้อนข้างละ 64 แถว ถ้าเพิ่มเพดาน โมดูลจะใช้ pyramid ลึกขึ้นได้ (สูงสุด 7 ชั้น) ซึ่งช่วยให้รอยเปลี่ยนแสงในบริเวณกว้าง เช่น ท้องฟ้า เนียนขึ้น แต่ใช้หน่วยความจำมากขึ้น

ผลวัดที่รันจริงบน JVM เดสก์ท็อป (OpenJDK 21, 2 CPU, single thread): ภาพ 12 MP จำนวน 3 ภาพ ใช้เวลา 7.8 วินาที และทำงานสำเร็จภายใต้ `-Xmx300m` ตัวเลขนี้ไม่ใช่ผลบนมือถือ ยังไม่ได้วัดบน Reno15 และคาดว่าจะช้ากว่านี้ ถ้าช้าเกินรับได้ ทางเลือกคือรวมภาพที่ความละเอียดต่ำลง หรือแบ่งแถบไปหลาย thread ในรอบถัดไป

## ผลทดสอบที่รันจริง

ผมรัน 14 เทสต์ใน `app/src/test/java/th/ogay/luma/hdr/HdrFusionQualityTest.java` ด้วย `javac` + JUnit 4.13.2 แยกจาก Gradle เพราะเครื่องที่ใช้พัฒนาไม่มี Android SDK ผลคือผ่านทั้ง 14 เทสต์ ภาพทดสอบสร้างจาก radiance map ที่รู้ค่า ผ่านกล้องจำลอง gamma 2.2 ที่ quantize 8 บิตและมี noise เล็กน้อย ผลวัดที่เทสต์พิมพ์ออกมามีดังนี้

|---|---|
| หน้าต่างที่ clip (std ของ luma) | EV 0 = 0.47, EV −2 = 12.17, ภาพรวม = 14.43 |
| มุมมืด (std ของ luma) | EV 0 = 1.19, ภาพรวม = 4.79 |

| ภาพเลื่อน (5, −3) | ด้านในต่างจากกรณีไม่เลื่อนเฉลี่ย 0.211 ระดับ |
| แถบเทียบกับทั้งภาพ | ต่างกัน 0 ทุกพิกเซล |

เทสต์ที่เหลือตรวจว่าภาพเดียวคืนค่าเดิม ภาพที่เหมือนกันทุกภาพ (รวม checkerboard 0/255) คืนภาพเดิมโดยไม่มี ringing ฉากเรียบไม่เกิดรอยด่าง ค่า `dx/dy` ที่ผิดทำให้ระบบถอยไปใช้ภาพอ้างอิงแทนการซ้อนขอบสองชั้น ภาพที่ไม่ซ้อนกันถูกข้าม และอินพุตที่ผิดสัญญาถูกปฏิเสธ

สิ่งที่ยังไม่ได้ทดสอบ: การ build ด้วย Gradle และ Android lint, ภาพ JPEG จริงจาก Reno15, เวลาและหน่วยความจำบนมือถือ, ความถูกต้องของสีเทียบกล้อง OPPO และภาพที่มีการสั่นแบบหมุน ภาพทดสอบสังเคราะห์ไม่มี tone curve เฉพาะ local tone mapping และการบีบอัด JPEG แบบภาพจริง

## ความเสี่ยงที่ควรรู้

Exposure fusion มักทำให้ภาพดูแบนลง (คอนทราสต์รวมต่ำ) เมื่อ bracket กว้าง ถ้าภาพดูจืดเกินไป ทางแก้คือใส่ tone curve หลัง merge ไม่ใช่ปรับในโมดูลนี้

ถ้าภาพอ้างอิงเบลอจากการสั่น ภาพรวมก็จะเบลอตาม เพราะทุกบริเวณที่ไม่ผ่านการเทียบจะถอยไปใช้ภาพอ้างอิง ควรเลือกภาพที่คมที่สุดเป็น frame 0

ถ้าวัตถุเคลื่อนที่กินพื้นที่มากกว่าครึ่งภาพ intensity mapping จาก histogram จะเพี้ยน และการปฏิเสธการเคลื่อนไหวจะไม่แม่น ควรทดสอบกรณีนี้บนเครื่องจริง
