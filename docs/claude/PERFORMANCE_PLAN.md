# แผนปรับปรุงประสิทธิภาพ Lumora

เขียน 2026-11-10 จากการอ่านโค้ดจริงใน branch `integration/glass-video-recovery`
ทุกข้อมีไฟล์ที่เกี่ยวข้องกำกับ ตัวเลขเป้าหมายต้องยืนยันด้วยการวัดบน Reno15 ก่อนและหลังแก้

---

## หลักการ

1. **วัดก่อนแก้** ทุกเฟสเริ่มด้วยตัวเลขก่อนแก้ และจบด้วยตัวเลขหลังแก้บนเครื่องจริง
2. **แก้จุดที่เปลืองที่สุดก่อน** ไม่ไล่ปรับเล็ก ๆ ทั่วแอป
3. **ทีละเรื่อง ทีละ build** ถ้าช้าลงหรือพัง จะรู้ทันทีว่าเพราะอะไร

## ปัญหาที่เจอในโค้ด เรียงจากหนักไปเบา

### ก. AI เพิ่มรายละเอียด (`ai/DetailSuperResolution.kt`, `ai/DetailRuntime.kt`)

ภาพ 12.5 MP (4096×3072) ถูกแบ่งเป็นช่อง 128×128 ได้ 768 ช่อง แต่ละช่องส่งเข้าโมเดลขนาด 200×200 (เผื่อขอบ 36 พิกเซลรอบด้าน)

| # | ปัญหา | ผลกระทบ |
|---|---|---|
| A1 | ทุกช่องสร้างอาร์เรย์ผลลัพธ์ใหม่ (`readFloat()` = 1.92 ล้านค่า ≈ 7.7 MB) | ทั้งภาพจองหน่วยความจำรวม ≈ 5.9 GB ทำให้ GC ทำงานหนักและเครื่องร้อน |
| A2 | ส่วนเผื่อขอบทำให้คำนวณเกินจริง 200²/128² = **2.44 เท่า** | งานจริงแค่ 41% ของที่โมเดลคำนวณ |
| A3 | โหมด ×2 ใช้โมเดล ×4 แล้วย่อลง | คำนวณผลลัพธ์เกินที่ใช้ **4 เท่า** |
| A4 | ถอดรหัส JPEG ทีละช่องด้วย `BitmapRegionDecoder` ช่องที่ติดกันถอดซ้อนกัน | ถอดรหัสซ้ำ ≈ 2.4 เท่า |
| A5 | ถอดรหัส → AI → วาด → เข้ารหัส ทำต่อกันทีละขั้นบนเธรดเดียว | GPU ว่างระหว่างรอ CPU และกลับกัน |
| A6 | `stopped()` อ่าน SQLite 2 ครั้งต่อช่อง | ≈ 1,500 คิวรีต่อภาพโดยไม่จำเป็น |
| A7 | แปลงพิกเซลเป็นค่าทศนิยมด้วยลูป Kotlin ทุกช่อง | งาน CPU ที่ย้ายไปทำในโมเดลได้ |
| A8 | ไม่ดูอุณหภูมิเครื่อง | ภาพใหญ่ทำให้เครื่องร้อนแล้วช้าลงเอง |

### ข. ความคืบหน้า AI ทำให้แกลเลอรีโหลดใหม่ทั้งหน้า (`Shots.kt`, `GalleryActivity.kt`)

ทุก 1% ที่ AI รายงาน → `Shots.changes` เปลี่ยน → แกลเลอรีเรียก `reload()` ซึ่งอ่านรายการทั้งหมดใหม่และสร้างตารางใหม่
ภาพเดียวทำให้โหลดใหม่ ≈ 100 ครั้ง นี่น่าจะเป็นสาเหตุหลักที่แกลเลอรีกระตุกระหว่าง AI ทำงาน
หน้ากล้องก็ฟังสัญญาณเดียวกัน (`loadThumb()`) แต่ตัดจบเร็ว จึงหนักน้อยกว่า

### ค. ทั้งแอป

| # | ปัญหา | ไฟล์ |
|---|---|---|
| C1 | release build ไม่เปิด R8 (ย่อและปรับโค้ด) | `app/build.gradle.kts` |
| C2 | ไม่มี Baseline Profile ทำให้เปิดแอปครั้งแรก ๆ ช้าและกระตุก | ยังไม่มี |
| C3 | งานไฟล์ทุกอย่างใช้คิว `fileIo` คิวเดียว การบันทึกภาพจึงอาจต้องรอแกลเลอรีหรือการตรวจคลิป | `Luma` application |
| C4 | เบลอ (`RenderEffect`) ทั้งหน้ารวมภาพพรีวิวกล้อง ทุกเฟรมของแอนิเมชัน | `GlassKit.blur/blurPulse` น่าจะเป็นต้นเหตุเบลอวูบตอนกดเมนู |
| C5 | สลับโหมดถ่ายใช้ `unbindAll()` แล้วผูกกล้องใหม่ทั้งชุด | `CameraActivity.kt` |
| C6 | APK รวม native lib ทุกสถาปัตยกรรม | `app/build.gradle.kts` |

## เฟส 0: วัดค่าเริ่มต้น (1 build)

1. ใส่ `android.os.Trace` ที่จุดหลัก: เปิดแอป, ผูกกล้อง, พรีวิวเริ่ม, ถ่าย, บันทึกเสร็จ, AI แต่ละขั้น
2. เก็บ FrameMetrics ของแกลเลอรีและหน้ากล้องเป็นไฟล์สรุป
3. ให้ผู้ใช้รัน: ถ่าย 1 ภาพ → AI ×2 และ ×4 → เลื่อนแกลเลอรี 10 วินาที → ส่งรายงาน
4. บันทึกตัวเลขลงเอกสารนี้เป็นค่าเริ่มต้น

## ลำดับที่แนะนำ

เฟส 0 → 1 → 2 → 4.1, 4.2 → 4.4–4.6 → เฟส 3

เหตุผล: เฟส 1–2 แก้ในโค้ดล้วน ได้ผลเร็วและวัดง่าย ส่วนเฟส 3 ต้องสร้างโมเดลใหม่และเทียบคุณภาพภาพ ใช้เวลามากที่สุด จึงทำหลังสุด
4.5 (R8) เสี่ยงที่สุดในฝั่งแอป เพราะอาจทำให้ไลบรารีบางตัวหายตอนรัน ต้องทดสอบครบทุกโหมด

## ความเสี่ยง

- **ไปป์ไลน์ขนาน (2.1)** ใช้หน่วยความจำเพิ่ม ≈ 2 แถว ต้องคุมขนาดคิว
- **NPU (3.4)** บางเครื่องไม่รองรับหรือให้ผลต่างจาก GPU ต้องมีทางสำรองเสมอ
- **R8 (4.5)** ถ้ากฎ keep ไม่ครบ แอปพังเฉพาะ release ต้องทดสอบ APK ที่ลงนามจริง
- **ลดขอบ (3.2)** อาจเห็นรอยต่อช่องในภาพที่มีลายละเอียด ต้องดูด้วยตาที่ 100%
